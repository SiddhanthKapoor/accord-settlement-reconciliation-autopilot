# Demo workspace and demo script

The thirteen files in `backend/data/demo_workspace/` are one month and a
half of one fictional business's paperwork, written by hand so the demo
shows the same thing every time. They are generated by
`backend/data/generate_demo_workspace.py`, which is deterministic: two
runs produce byte-identical output, and the observation point is a pinned
constant (`AS_OF = 2026-04-15`) rather than `datetime.now()`, so nothing
here decays.

Regenerate and self-check:

```bash
python backend/data/generate_demo_workspace.py            # write the files
python backend/data/generate_demo_workspace.py --verify    # + detector + engine
```

`--verify` feeds every generated file back through the real
`app.ingest.reader.read_table`, `app.ingest.schema.detect_schema`,
`app.ingest.mapper.map_rows` and `app.engine.batch.process_batch`, with
`ACCORD_AI_DISABLED=1` so no key is read and no network call is made. It
fails loudly if any invariant below stops holding.

## 2. Scenarios

Every record id below is the id the engine will show, i.e. what
`mapper.map_rows` produces as `order_id`. "Correct outcome" is what the
construction of the data entails; it is not a measurement.

### S1 — the boring majority

**Records:** `ORD-7001`…`ORD-7020`, `ORD-7032`, `ORD-7036`, `ORD-7042`,
`SH-88201`…`SH-88210`, `SH-88212`, `BR-4482`, `BR-4483`, `BR-4484`,
`ZB-6101`, `ZB-6102`, `ZB-6106`.

40 of 54 ledger records resolve to a single settlement deterministically
— on an exact normalized reference, or (for `ORD-7036`) on the one of two
records sharing that reference whose amount agrees — and pass every
financial check. **Correct outcome: RECONCILED, with no model call.** This is the point of the demo, not the
filler around it: the arithmetic does the work, and the model is only
reached for the residue.

### S2 — resolvable only by a semantic model

The identifier is genuinely absent or in a different numbering system.
The generator asserts, using the engine's own `normalize.reference_cores`
and `normalize.references_comparable`, that the two sides share no digit
run and that their identifier widths are not comparable — so no
deterministic path can recover the link.

| | |
|---|---|
| **S2a** | `ORD-7021` — books say `INV-3055`, "Annual cloud platform renewal — Northwind Retail Private Limited", ₹31,200.00 on 2026-03-17. The only trace of the money is one HDFC line on 2026-03-18: `NEFT INWARD CLDPLTFRM RENEWAL NORTHWND`, ref `UTR774120`. Cores `{3055}` vs `{774120}` — disjoint, widths 4 vs 6. |
| **S2b** | `ZB-6104` — Zoho invoice "Marketplace channel settlement week 12 — Kartway Seller Services", ₹27,450.00. The settlement is a marketplace payout row `KWY-88213`, "Seller services payout for week 12". Cores `{6104}` vs `{88213}` — disjoint, widths 4 vs 5. |

**Correct outcome for both: RECONCILED via `SEMANTIC_CONFIRMED` when the
model answers SAME at or above the 0.85 confidence gate; HUMAN_REVIEW
otherwise.** Never a silent match — `PolicyConfig.ai_confidence_threshold`
is enforced in `policy.py`, not by the model.

### S3 — the identical-amount trap

`ORD-7031` (`INV-3042`, "Gift card bulk purchase corporate", ₹8,650.00,
2026-03-24) has **no settlement anywhere**. One day later, `INV-3117` — a
completely different customer's refrigeration unit deposit — settles
through Cashfree for **exactly ₹8,650.00**. The two references live in
the same numbering system and disagree.

**Correct outcome: `ORD-7031` → EXCEPTION, refused, and the refusal names
the record it looked at and why it rejected it. `ORD-7032` (the real
owner of `INV-3117`) → RECONCILED.** Matching on amount and date would
double-count ₹8,650 and orphan a real order. The refusal is deterministic
— no model call is spent on it.

### S4 — aggregated settlement

Two different aggregations, because they are two different real shapes.

**S4a, detected by the engine.** `BR-4471` (₹42,300.00), `BR-4472`
(₹27,850.00) and `BR-4473` (₹9,415.00) are three Tally invoices to the
same distributor. One ICICI escrow credit on 2026-03-23, ref `UTR881318`,
is ₹79,565.00 — the exact sum. The generator asserts both that the sum is
exact and that **no other combination of two or three possibly-unmatched
records sums to any settlement in the population**, because a lump sum
that decomposes two ways is not evidence of anything.

**Correct outcome: all three → HUMAN_REVIEW / `AGGREGATED_SETTLEMENT`.**
The grouping is proposed, never applied.

**S4b, the fee-and-tax tie-out.** `INV-3010`, `INV-3011` and `INV-3012`
settle in one Razorpay batch on 2026-03-11. Gross ₹33,150.00 + ₹18,400.00
+ ₹9,900.00; after each row's recorded fee and tax the nets are
₹32,367.66 + ₹17,965.76 + ₹9,666.36 = **₹59,999.78**, which is exactly
the HDFC credit `UTR774008` on the same day. Asserted to the paisa in the
generator.

The three orders reconcile individually on their references, so the
engine does not need to decompose this one — the tie-out is there for a
human to check the bank line against the batch, which is what a finance
operator actually does.

### S5 — pending vs missing

Both pinned to `AS_OF = 2026-04-15`, which is also the latest settlement
date in the workspace — the value `batch.process_batch` derives when the
upload path does not pass one. The cutoff is `AS_OF − 2 days`
(`PolicyConfig.settlement_expected_days`).

| | |
|---|---|
| **S5a pending** | `ZB-6107`, ₹15,750.00, invoiced 2026-04-14. A settlement is not due until 2026-04-16. **Correct outcome: EXCEPTION / `PENDING_SETTLEMENT`, severity LOW — "wait", not "chase the provider".** |
| **S5b missing** | `ORD-7034` (`INV-3061`), ₹18,650.00, 2026-03-19, with no lookalike anywhere in the population. **Correct outcome: EXCEPTION / `MISSING_SETTLEMENT`.** |

### S6 — fee/tax arithmetic

`BR-4481`, ₹7,700.00, settled through PayU. The file states gross
₹7,700.00, service charge ₹154.00, GST ₹27.72 and **net ₹6,800.00**,
while gross − fee − tax is ₹7,518.28. A payout file that does not add up.

**Correct outcome: EXCEPTION / `FEE_TAX_INCONSISTENT`, severity HIGH.**
The match itself is fine — this is an arithmetic failure on a correctly
matched pair.

### S7 — refunds

| | |
|---|---|
| **S7a offset, consistent** | `ORD-7036` (`INV-3065`), ₹11,000.00 with ₹2,500.00 refunded. The Razorpay row records the same refund and nets it out; the refund report carries the same reference at ₹2,500.00, so two settlements share the reference and exactly one matches on amount. **Correct outcome: RECONCILED, classification `DISAMBIGUATED_BY_AMOUNT`.** |
| **S7b chargeback not booked** | `ORD-7037` (`INV-3072`), ₹16,800.00, booked as fully paid. The gateway recorded a ₹4,200.00 chargeback and the refund report carries it as `(4,200.00)`. **Correct outcome: EXCEPTION / `REFUND_MISMATCH`.** |

### S8 — the same payment in two sources

`ORD-7104` (`INV-3050`), ₹24,999.00. It appears once in
`razorpay_settlements_mar_apr.csv` as a settled payment, and once in
`bank_hdfc_current_mar2026.csv` on 2026-03-30 as
`NEFT INWARD RAZORPAY SETL NORTHWND RTL` — where the bank's `Ref No`
field carries the remitter's reference, `INV-3050`, as inward NEFT lines
often do.

**Correct outcome: HUMAN_REVIEW / `AMBIGUOUS_MATCH`.** Two settlement
records claim the same reference at the same amount; the system cannot
tell one payment reported twice from two payments, so it refuses and
says which two records are in contention. This is a real finding, not a
bug in the data.

### S9 — currency mismatch

`ORD-7038` (`INV-3068`), booked as **USD** 1,200.00; the gateway settled
**INR** 1,200.00. Minor units carry no currency, so every other check
passes on this pair. **Correct outcome: EXCEPTION / `CURRENCY_MISMATCH`,
severity HIGH.**

### S10 — ambiguous even for the model

`SH-88211`, ₹4,120.00, 2026-03-25, notes "Counter sale payment received".
One HDFC credit on 2026-03-26 for exactly ₹4,120.00:
`UPI/COLLECT/9911/PAYMENT RECEIVED`. Both sides are vague; the identifier
namespaces (`88211`, width 5, vs `UTR774501`, width 6) are not
comparable, so there is nothing to contradict and nothing to confirm.

**Correct outcome: HUMAN_REVIEW.** Not everything is solvable, and a
system that resolves this one confidently is guessing.

### S11 — truncated reference

`ORD-7040` (`INV-3062`), ₹13,475.00. Cashfree recorded the order id as
**`INV-306`** — truncated. `306` is three digits, below
`normalize.MIN_REFERENCE_CORE_DIGITS`, so it is not an identifier core at
all: exact matching misses, and nothing contradicts.

**Correct outcome: RECONCILED via `SEMANTIC_CONFIRMED` if the model is
confident at or above 0.85; otherwise HUMAN_REVIEW /
`LOW_CONFIDENCE_MATCH`.** Both are correct behaviour; a silent
low-confidence reconcile is not.

### S12 — duplicate file

`bank_icici_escrow_mar2026 (1).xlsx` is a byte-for-byte copy of
`bank_icici_escrow_mar2026.xlsx` (same SHA256, recorded in
`_manifest.json`). **Correct outcome: the duplicate is detected before it
reaches reconciliation and is not ingested twice.**

If it *is* ingested, every bank line in it is duplicated, which is
visible rather than silent — but the recommended upload set for the video
is the twelve data files, adding the copy only when demonstrating the
duplicate-file check.

## 4. Detection: what is clean and what asks

All twelve data files resolve both required fields (`amount`, `date`)
with no user input, so none of them blocks a run. One of them still needs
a confirmation before it is useful. Details worth knowing on stage:

- **`orders_shopify_export.csv` needs one confirmation.** The detector
  reads a bare `Name` column as a counterparty, which is the more common
  reading; in a Shopify export it is the order number. Required fields
  (`amount` = `Total`, `date` = `Created at`) are both resolved, so the
  run is not blocked — but until `Name` is mapped to `reference`, the
  twelve Shopify orders have no cross-system identifier and read as
  missing settlements. **This is deliberate and it is a good demo beat:
  the system asks instead of guessing.** `Financial Status` is also
  unmapped; it is corroborating detail and does not change any outcome.
- **`payu_settlements_mar.csv`** has no header the detector recognises as
  a date. `Added On` is recovered by content inspection at confidence
  0.60 and reported as such — worth pointing at, because it is the
  detector saying *why* it thinks a column is a date.
- **`kartway_marketplace_payout.csv`** maps `payout-date` to
  `settlement_date` and rescues `settlement-start-date` as the
  transaction date. `selling-fees` is left unmapped, so the payout's fee
  is not double-counted against a `total` that is already net.
- **`bank_hdfc_current_apr2026.xlsx`** opens with two title lines and a
  blank row; `reader.find_header_row` locates the real header on row 4
  and says so in its notes.
- **`tally_sales_register.csv`** and all three bank statements are
  detected as paired debit/credit columns, so a withdrawal is read as
  money out rather than as another inflow.

## 5. A five-step demo sequence

**Step 1 — upload the mess (about 40 seconds).**
Drag in all twelve data files at once. Different vendors, two file
formats, paise in one file and `₹1,23,456.78` in another, a bank export
with a title block. Point out that nothing was pre-configured: the
schema of each file is inferred, and each guess carries a confidence and
a reason.

**Step 2 — the one question it asks.**
Open `orders_shopify_export.csv` and show `Name` detected as a
counterparty at high confidence. Confirm it as the reference. This is the
argument for the whole ingestion design: the system does not silently
guess an identifier column, because a reconciliation tool that
mis-reads a column is worse than one that asks.

**Step 3 — run it, and let the boring part be boring.**
40 of 54 records reconcile on exact references with no model call. Do not
dwell. Say the number, say that the model was not involved, move on. The
credibility of the interesting cases depends on the ordinary ones being
handled by arithmetic.

**Step 4 — the refusal (`ORD-7031`).**
Open the exception. There is an ₹8,650.00 credit one day later, the
amount matches to the paisa, and the system refused it — because
`INV-3042` and `INV-3117` are references from the same numbering system
that name different transactions. Then open `ORD-7032` and show that
₹8,650.00 settlement matched to its actual owner. This is the moment
worth the most: the system declined free-looking money and said why.

Follow it immediately with `ZB-6107` (pending, not missing — a
settlement is not due until 2026-04-16) and `BR-4481` (the payout file's
own arithmetic is off by ₹718.28). Three refusals of three different
kinds, all deterministic.

**Step 5 — where the model earns its place (`ORD-7021`).**
Books: "Annual cloud platform renewal — Northwind Retail Private
Limited", ₹31,200.00. Bank: `NEFT INWARD CLDPLTFRM RENEWAL NORTHWND`,
`UTR774120`. No shared identifier — the invoice number is four digits,
the UTR is six, they are not even the same kind of thing. Show the
investigation trace, the confidence, and that policy, not the model,
decided the outcome. Then show `SH-88211`, where both sides say nothing
useful and the correct answer is "a person should look at this".

Close on the aggregation (`BR-4471`/`BR-4472`/`BR-4473` → `UTR881318`,
₹42,300 + ₹27,850 + ₹9,415 = ₹79,565.00 exactly) as a proposal, not an
auto-match, and on the audit trail.

If there is time for a sixth beat: re-upload
`bank_icici_escrow_mar2026 (1).xlsx` and let the duplicate-file check
catch it.

## 6. What this data is not

- It is not an accuracy measurement. Ground truth here is the
  construction of each record, and the correct outcomes in §2 follow from
  that construction. Accuracy numbers come from
  `backend/evaluations/` and `docs/EVALUATION_METHODOLOGY.md`, on held-out
  data this workspace has no part in.
- It is not tuned against the engine. No threshold was changed to make a
  record land where this document says it should; where the offline run
  in §3 differs from §2, the difference is reported rather than papered
  over.
- Every business name in it is fictional.
